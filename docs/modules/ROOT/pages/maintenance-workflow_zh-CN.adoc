= Codex++ Linux 适配维护流程
:toc:
:toclevels: 2

简体中文 | xref:maintenance-workflow.adoc[English]

本文档是 `906341774/CodexPlusPlus-for-Linux` 的正式维护流程。
它优先保证适配工作可复查、可中止、可恢复，而不是追求长时间无人值守的全自动化。

本流程替代之前以全流程自动适配为默认目标的实验性工作流。
旧的自动化页面仍可作为历史参考，但不得在没有维护者明确要求时作为默认执行方案。

== 背景

`v1.2.28` 基线适配期间，长事务自动化暴露出几个结构性问题：

* 上下文压缩后，Agent 容易丢失精确阶段状态，从环境检查重新开始，造成大量重复工作。
* GUI、Computer Use、MCP 或容器显示通道失败时，容易被误判为 Codex++ 兼容性缺陷。
* 自动化范围过大，一个运行中同时承担构建、安装、GUI 操作、问题定位、补丁编写、文档更新、发布验收和推送。
* 缺少硬性熔断条件，导致基础设施异常可能继续扩散成无证据补丁。

因此，当前维护策略回退到“手动主导、脚本辅助、Podman 隔离验证”的模式。

== 基本原则

* 每一轮只固定一个上游 Codex++ 基线版本。
  调试过程中即使上游发布新版本，也不得切换基线。
* Podman 容器仍是默认测试环境。
  适配修复应先在容器内验证，再考虑覆盖宿主机安装目录。
* Agent 不再自主遍历所有 GUI 功能。
  GUI 问题以维护者实际使用反馈、截图、日志和定点复现为主要入口。
* 每个补丁都必须有证据链。
  证据链至少包括复现现象、根因判断、修改范围和验证结果。
* 没有证据的修改不能进入 Antora snippet manifest。
* 自动化只能执行边界清晰的单阶段任务。
  不允许把完整适配发布过程作为一个不设限的长事务。

== Prompt 草稿目录规则

`.ai_prompts_draft/` 是维护者存放对话提示词草稿的私有工作区。
其中可能有废稿、过时指令、失效假设或临时实验文本。

硬规则：

* 未经维护者明确指示，Agent 默认禁止读取 `.ai_prompts_draft/`。
* 如果维护者指定某个提示词文件，只能读取该文件。
* 不得把 `.ai_prompts_draft/` 中的内容自动提升为项目事实、流程要求或发布门禁。
* 若提示词草稿与正式文档冲突，以本文档、README、Antora 页面和当前用户指令为准。

== 维护模式

=== manual-stable

`manual-stable` 是当前默认模式。

适用场景：

* 追随新的 Codex++ 上游基线版本；
* 修复用户在实际使用中发现的 Linux 适配问题；
* 验证某个具体功能，例如 Fast 按钮、脚本市场、Pure API 配置同步。

流程：

. 固定基线版本，例如 `v1.2.29`。
. 更新或恢复 `CodexPlusPlus/src` 和 `codex-desktop-linux/src` 中的源码快照。
. 使用现有脚本完成静态检查、patch apply check 和白盒测试。
. 在 Podman 容器内完成 CodexDesktop 与 Codex++ 构建、安装和基本启动。
+
对于 Codex Desktop 的直接 `make build-app` 构建路径，PowerShell 构建流程必须先写入本地 gitignored 的 `linux-features/features.json`，同时导出 `CODEX_LINUX_FEATURES` 和 `CODEX_LINUX_FEATURES_CONFIG`，并在执行 `make build-app` 前让 `CODEX_LINUX_FEATURES_CONFIG` 指向该文件。
构建产物复制到 `$HOME/opt/CodexDesktop` 后，必须验证两个 build metadata 文件：
+
[source,text]
----
$HOME/opt/CodexDesktop/.codex-linux/build-info.json
$HOME/opt/CodexDesktop/resources/codex-linux-build-info.json
----
+
两个文件都必须记录预期启用的 Linux feature ids。
此直接构建路径不得只依赖环境变量中的 feature 列表；如果 metadata 会显示 `Enabled features: None`，必须停下修复构建流程后再继续。
. 根据维护者反馈选择一个具体问题做复现和修复。
. 将验证通过的修改整理为 Antora snippet 或脚本改动。
. 提交前总结已解决问题、已验证功能和未解决问题。
. 推送到维护者 fork，并创建对应 tag 或 hotfix tag。

=== bounded-auto

`bounded-auto` 是允许继续探索的自动化模式，但一次只能完成一个阶段。

允许的阶段示例：

* 仅构建 AlmaLinux 9 Podman 测试镜像；
* 仅运行安装脚本 selftest；
* 仅在干净上游源码上重放 patches；
* 仅验证一个 GUI 功能；
* 仅生成某个版本的发布日志草案。

硬限制：

* 每次运行必须声明阶段名称、输入、输出和停止条件。
* 同一阶段在输入未变化时最多重复一次。
* 失败后必须产出失败分类，而不是继续修补代码。
* GUI 或 Computer Use 失败不得直接推导为 Codex++ 兼容性 bug。
* 需要跨越阶段时，必须先给出阶段报告并等待维护者确认。

=== full-auto

`full-auto` 暂停使用。

只有在 `bounded-auto` 连续多个版本稳定、不会重复环境检查、不会误判 GUI 基础设施失败、并能可靠保存阶段状态后，才考虑恢复。

== 阶段状态文件

后续若恢复自动化，必须使用持久化状态文件记录运行阶段。
建议路径：

[source,text]
----
.adaptation-runs/<run-id>/state.json
----

最低字段：

[source,json]
----
{
  "run_id": "2026-07-03-v1.2.29",
  "baseline": "v1.2.29",
  "mode": "bounded-auto",
  "stage": "patch-replay",
  "completed_stages": ["source-sync", "installer-selftest"],
  "last_success_evidence": "logs/patch-replay.ok.txt",
  "blocked_reason": null,
  "repeat_count_for_current_stage": 0
}
----

上下文压缩或任务恢复后，Agent 必须优先读取该状态文件。
若状态文件不存在或与当前工作树不一致，必须停下说明，不得从头重跑完整流程。

== GUI 失败分类

在判断某个现象是 Codex++ 适配 bug 前，必须先排除 GUI 基础设施失败。

基础设施失败包括：

* Computer Use 调用未到达 MCP；
* 截图时间戳不更新；
* 目标窗口不存在或 PID 已退出；
* `ydotool` 或 `/dev/uinput` 不可用；
* X11、DBus、portal 或容器显示桥异常；
* CDP 端口连到宿主机实例或旧实例；
* CodexDesktop 界面卡死，无法响应基本点击。

这些情况只能结论为“测试基础设施失败”。
必须先修复测试环境或请求维护者人工介入，不能写 Codex++ 兼容性补丁。

== 发布和 tag 策略

一个新基线做到初步可用后，应先进行一次 Git 同步。

正式基线 tag：

[source,text]
----
v1.2.29
----

后续 hotfix tag：

[source,text]
----
v1.2.29-fix-0001
v1.2.29-fix-0002
----

发布日志必须包含：

* 对应的上游 Codex++ 版本；
* 对应的 `codex-desktop-linux` 源码快照或提交；
* 本轮解决的问题；
* 本轮实际验证过的功能；
* 未验证功能；
* 已知问题；
* 构建产物或 Podman 测试环境是否导出。

不要移动已经推送的正式 tag。
如果正式 tag 后发现问题，使用 hotfix tag 追加修复。

== 推送前检查

推送前至少检查：

* 没有真实 token、私钥、授权头或账号隐私信息；
* `.tmp/`、`.cache/`、Podman 运行缓存和临时测试目录未入库；
* `.ai_prompts_draft/` 未入库，且没有被当作正式流程依据；
* 如果加入构建产物，必须明确说明用途、来源和校验值；
* 若源码快照入库，说明对应上游版本或提交。

== 中止条件

遇到以下情况必须停下报告：

* Podman 测试容器无法启动；
* 容器内 GUI 基础设施不可用；
* Computer Use 连续失败，且无法证明请求确实到达 MCP；
* 上下文压缩后无法确认当前阶段；
* 同一阶段重复执行超过限制；
* 需要改变维护者明确指定的路径、版本或测试语义；
* 发现可能泄漏隐私或凭据。

== 当前执行建议

在确认自动化问题来源之前，下一轮上游基线适配应使用 `manual-stable`。
Agent 可以协助运行脚本、分析日志、写补丁和整理发布日志，但不应自主启动长时间全流程自动适配。

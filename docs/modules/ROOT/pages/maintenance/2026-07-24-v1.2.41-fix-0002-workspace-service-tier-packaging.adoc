= v1.2.41-fix-0002 会话目录、Fast 切换与发行包修复验收
:toc:
:toclevels: 2

== 结论

`v1.2.41-fix-0002` 修复了两个可在真实 Linux 用户状态中复现的问题：

* Codex++ 曾把 POSIX 工作区路径写成反斜杠形式，并留下 `rootPaths` 为空的
  `local-projects`，导致对应项目侧栏持续显示“暂无对话”；
* Codex++ 的 Fast/Standard 注入会无限等待新版 Desktop 中可能永久 pending
  的 `setting-storage.n()`，最终无法获得当前模型并拒绝切换。

本轮还复核并固定了 Linux features 的直接构建流程，重新生成 Debian 10
兼容 DEB、RHEL 9 兼容 RPM 和便携 7z，并通过独立 Podman 容器中的
`Xvfb + xdotool` GUI 验收。DEB 截图验收额外发现 Debian 10 最小环境缺少
CJK 字体，因此包现在推荐安装 `fonts-noto-cjk`。

最终发行 payload 的 Desktop ASAR 仍为已验收的 v1.2.41 基线 ASAR；
未把陈旧 ASAR 或未达最终压缩参数的中间包混入 Release assets。

== “暂无对话”根因与修复

=== 根因

旧 `codex_app_state` 路径标准化无条件执行
`replace('/', '\\')`。这对 Windows 路径成立，但在 Linux 上会把
`/home/deck/project` 变成 `\home\deck\project`。

Codex++ 随后以错误路径计算 `local-<sha256-prefix>` 项目 id，并在
`.codex-global-state.json` 中留下如下不完整记录：

[source,json]
----
{
  "id": "local-...",
  "name": "\\home\\deck\\project",
  "rootPaths": []
}
----

`local_thread_catalog` 和 Desktop 项目状态实际使用 POSIX 路径。错误项目 id、
空 `rootPaths` 与正确 catalog 行无法关联，因此项目入口存在，但侧栏只能
显示“暂无对话”。provider sync 也会保留已有的单反斜杠 POSIX 路径，不能
自行收敛这类历史状态。

=== 修复边界

`085-linux-workspace-state-paths.patch` 现在：

* 在非 Windows 平台保留 `/`，只把已确认的单前导反斜杠 POSIX 遗留路径
  转回 `/`；
* 继续正确处理 Windows drive、UNC 和 `\\?\` 路径；
* 只修复同时满足错误 id 与 `name` 哈希一致、`rootPaths` 为空、对应正确
  POSIX 路径已存在于 saved roots 的 `local-projects`；
* 以正确 POSIX 路径重新计算项目 id，填回 `rootPaths`，同步替换
  `project-order` 和本地 `selected-project`；
* 保留自定义项目、已有非空 roots、哈希不匹配记录和冲突目标，不做宽泛
  猜测性迁移；
* provider sync 同步把历史单反斜杠 POSIX cwd 转回 `/`。

测试覆盖被修复项目、自定义项目、非空项目、哈希不匹配项目、引用更新和
重复执行。宿主机另有一个已确认的工作区重命名，发布后只对该精确旧路径与
新路径执行一次性映射；它不会被固化为通用自动重命名规则。

== Fast/Standard 根因与修复

新版 Desktop 的 `setting-storage` module 可以成功加载，但
`settingStorage.n({ key: "default-service-tier" })` 在部分启动状态中永远
保持 pending。旧注入代码在读取完成前不会进入后端 settings 或 config
fallback，模型状态一直为空，点击 Fast/Standard 后显示“当前模型未获取”或
“当前模型未读取”。

注入现在为 Desktop storage read 设置 1500 ms 上限：

* 正常返回时仍优先使用 Desktop setting storage；
* 超时或读取失败时调用 Codex++ `/settings/get`，读取安全的
  `codexDefaultServiceTier`；
* helper 不可用时继续使用既有 `codexStateCall` fallback；
* 模型支持列表保留 GPT-5.4、GPT-5.5、GPT-5.6 及三个 GPT-5.6 变体；
* 官方 Desktop Fast 控件不被 Codex++ 清理逻辑移除。

回归测试使用一个真实永久 pending 的 `setting-storage` module，证明超时后
能得到 `priority`，并保护正常 storage、后端 settings、helper 超时与官方
控件共存路径。

包安装后的实际 `xdotool` 点击验收依次切换全局 Fast 和全局 Standard，
状态文本正确，页面中没有“当前模型未获取”“当前模型未读取”或“无法切换”。

== Linux features 构建结论

`Enabled features: None` 不是 PowerShell 调用方完全没有传 feature list。
根因是 `linux-features.js` 的无 config 直接构建路径没有把仅来自
`CODEX_LINUX_FEATURES` 的列表稳定带入后续 metadata 生成。

`Build-CodexDesktopLinux.ps1` 已把修复固定为标准流程：

* 动态解析或接受显式 feature ids；
* 写入 gitignored 的 `linux-features/features.json`；
* 同时导出 `CODEX_LINUX_FEATURES` 与 `CODEX_LINUX_FEATURES_CONFIG`；
* 让 config 环境变量指向刚写入的文件后再执行 `make build-app`；
* 安装前检查 `.codex-linux/build-info.json` 与
  `resources/codex-linux-build-info.json` 均记录相同的非空 feature list。

最终 payload 的两份 metadata 字节一致，均记录 29 个 Linux features。

== 包兼容性与 CJK 修复

=== Debian 10 与 RHEL 9 ABI

Codex++ Manager 上游源代码以 WebKitGTK 4.1/libsoup 3 为首选。稳定发行版
构建流程会在完整 4.1 开发 ABI 可用时使用原生 4.1，否则使用已验证的
WebKitGTK 4.0/libsoup 2.4 compatibility bridge。

本轮 Debian 10 兼容 Manager 最终动态依赖为：

[source,text]
----
libwebkit2gtk-4.0.so.37
libjavascriptcoregtk-4.0.so.18
libsoup-2.4.so.1
RUNPATH=$ORIGIN/manager-runtime
----

DEB 和 RPM 中共检查 40 个 x86-64 ELF，最高 GLIBC 需求为
`GLIBC_2.28`，无超限文件。RPM 兼容目标仍是 RHEL 9 及其兼容发行版，
不把 Fedora 43 声明为兼容目标。

=== Debian CJK 字体

第一次 DEB GUI 截图中 Codex++ Manager 的中文标签显示为方框。应用和
Manager 进程均正常，根因只是 Debian 10 最小容器没有 CJK 字体。

先新增失败的 shell smoke 合同，要求 control 包含：

[source,text]
----
Recommends: fonts-noto-cjk, zenity, kdialog
----

实现后完整 `scripts_smoke.sh` 通过。对候选 DEB 执行真实 remove 后的首次
`apt install`，APT 自动下载并安装
`fonts-noto-cjk 1:20170601+repack1-3+deb10u1`。新的 Xvfb 截图中中文正常
渲染，Manager 窗口标题为 `Codex++ 管理工具`。

== 宿主迁移边界

发布 tag 和 GitHub Release 完成前不覆盖宿主安装。发布后将：

. 停止 CodexDesktop 与 Codex++；
. 备份当前 `.codex-global-state.json` 和 latest safe snapshot；
. 仅对已确认的旧、新竞赛目录执行精确重命名映射；
. 让新 launcher 自动修复其余五个错误 POSIX local projects；
. 使用原子替换保留现有用户数据目录的 device、inode 和哨兵；
. 重新启动并确认项目侧栏不再显示错误的“暂无对话”，Fast/Standard 可切换，
  两个菜单入口有图标且 Manager 正常。

宿主最终证据将在 Release 发布并完成上述步骤后追加到本文档；已经发布的
`v1.2.41-fix-0002` tag 不会移动。

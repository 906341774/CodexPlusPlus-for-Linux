= Recurring adaptation workflow
:toc:
:toclevels: 2

English | xref:adapter-workflow_zh-CN.adoc[简体中文]

This project is a Linux adaptation layer for upstream `BigPizzaV3/CodexPlusPlus`.
It should behave like a platform port, not like a separate product.
Every recurring update must therefore answer two questions:

IMPORTANT: The current official workflow is xref:maintenance-workflow.adoc[Codex++ Linux Adaptation Maintenance Workflow].
This page is retained as historical and experimental automation reference; do not use it as the default execution plan unless the maintainer explicitly asks for it.

* Does the current adapter still apply cleanly to the pinned upstream version?
* Do the original Codex++ features still produce their expected Linux UI and runtime effects?

The machine-checkable feature contract is stored in xref:attachment$feature-matrix.json[`feature-matrix.json`].

== Regular cadence

Run the scheduled workflow at least weekly, and run it manually whenever upstream Codex++ publishes a release or materially changes launcher, manager, renderer injection, user scripts, install logic, or API profile handling.
Each run must freeze one upstream baseline for the whole adaptation round. Do not switch to a newer upstream release in the middle of the same round just because another release appears during debugging; finish the pinned baseline first, then start a separate round if the maintainer asks to follow the newer release.

The GitHub Actions entry point is `.github/workflows/adaptation-regression.yml`.
It is intentionally split into validation and release phases: scheduled runs validate, while publishing to a maintained fork remains an explicit maintainer action.

== Update procedure

. Record the current adapter state.
  Tag the current repository before syncing new upstream code. Use the adapter version as the tag name when the repository version already matches the current upstream baseline.
. Fetch or restore the pinned upstream Codex++ source.
  If an older cached source tree is available, first reproduce the previous green test result there.
. Run the local workflow contract.
+
[source,bash]
----
HOME=/tmp/codexpp-workflow-home \
XDG_DATA_HOME=/tmp/codexpp-workflow-data \
XDG_CONFIG_HOME=/tmp/codexpp-workflow-config \
XDG_CACHE_HOME=/tmp/codexpp-workflow-cache \
pwsh -NoLogo -NoProfile -File scripts/developer/Test-AdapterWorkflow.ps1
----
. For the common local smoke path, run the combined adapter regression entry.
+
[source,bash]
----
./scripts/developer/run-adapter-regression.sh
----
. Run the installer selftest.
+
[source,bash]
----
HOME=/tmp/codexpp-installer-home \
XDG_DATA_HOME=/tmp/codexpp-installer-data \
XDG_CONFIG_HOME=/tmp/codexpp-installer-config \
XDG_CACHE_HOME=/tmp/codexpp-installer-cache \
pwsh -NoLogo -NoProfile -File scripts/developer/Installer-and-Manager.ps1 selftest -NonInteractive -NoTui
----
. Apply all production snippets and regression snippets to a clean upstream source tree.
  `git apply --check` must pass for every patch before building.
. Run the white-box regression tests from `900-regression-tests`.
  At minimum, run the focused Rust tests that cover path resolution, CDP target selection, launcher environment, Pure API config sync, renderer injection, Fast button placement, and user-script location aliasing.
. Prepare the AlmaLinux minimal container environment.
  The rootless Podman storage must use the user-level XFS loop mount when the home directory is backed by NFS:
+
[source,bash]
----
sudo mount -o loop,rw "$HOME/.local/share/podman-loop-storage/containers-storage.xfs" "$HOME/.local/share/containers"
----
+
  Stop and report if this mount, the AlmaLinux image pull, or container creation fails.
  A missing Podman environment is a foundational blocker, not a reason to replace the required validation with a source-only workaround.
. Build and install `ilysenko/codex-desktop-linux` in the container using the PowerShell procedure from the prompt and README.
  The validation install root is `$HOME/opt/CodexDesktop`; this path is the Codex app root itself and must not be rewritten as `$HOME/opt/CodexDesktop/codex-app`.
. Run the AlmaLinux minimal container install cycle.
  The cycle must cover non-interactive install, update, uninstall, and the interactive prompt path where Enter accepts each configured default.
  Pass the Codex Desktop root explicitly and leave the Codex++ install path unspecified so the script default is tested:
+
[source,powershell]
----
pwsh ./scripts/developer/Installer-and-Manager.ps1 -Action install -CodexDesktopRootPath "$HOME/opt/CodexDesktop" -NonInteractive
pwsh ./scripts/developer/Installer-and-Manager.ps1 -Action update -CodexDesktopRootPath "$HOME/opt/CodexDesktop" -NonInteractive
pwsh ./scripts/developer/Installer-and-Manager.ps1 -Action uninstall -CodexDesktopRootPath "$HOME/opt/CodexDesktop" -NonInteractive
----
. Run GUI validation.
  Start Codex Desktop through the newly installed Codex++ Manager, then verify the feature matrix black-box checks by Computer Use screenshots and CDP DOM assertions.
  In the `--network=host` Podman fixture, the validation command must set an isolated `CODEX_WEBVIEW_PORT` in addition to unique Codex++ CDP debug and helper ports; otherwise the launcher may collide with, or accidentally inspect, a host Codex Desktop instance.
  Stop and report if Computer Use or equivalent GUI automation repeatedly fails after the application is running; GUI evidence is part of the release gate.
. Update the snippets, feature matrix, and workflow docs if any upstream change makes a patch unnecessary or insufficient.
. Clean temporary source trees, container images, caches, and test files before committing.
. When the release gate is green, clear only the CodexDesktop and Codex++ debug payloads from the prepared container, then archive the prepared test container with non-solid maximum 7z compression into an Antora attachment subdirectory for the next adaptation round.
. Commit and push only after the feature matrix has been checked off for the target version.

== Stop and report conditions

The maintainer may ask for mostly automatic execution, but the following conditions must stop the adaptation run and be reported clearly:

* the user-level XFS loop storage cannot be mounted for rootless Podman;
* AlmaLinux minimal cannot be pulled or started;
* the explicit `-CodexDesktopRootPath "$HOME/opt/CodexDesktop"` install path cannot be validated;
* Computer Use or another GUI validation channel repeatedly fails after the app starts;
* the validation would require changing the requested workflow semantics rather than fixing the adapter.

When one of these happens, do not silently substitute a weaker validation layer.

== Patch categories

Compatibility patches live under `docs/modules/ROOT/attachments/patches/compatibility/` and are treated as required for Linux support. Enhancement patches live under `docs/modules/ROOT/attachments/patches/enhancements/` and are reserved for future user-selectable features.

== Required GUI evidence

The final validation report for a release should include screenshots or DOM assertions for these Linux-visible behaviors:

* Codex++ Manager health checks show Linux launcher and manager entries as present.
* Codex Desktop launches through Codex++ without a blank page.
* Plugins navigation is clickable and has no debug suffix.
* Plugin details open without an error page.
* Pure API profile switching updates `$HOME/.codex/config.toml`.
* Delete Conversation does not trigger a full page refresh.
* The Fast service-tier badge appears in the Linux composer footer and remains clickable.
* `Codex Context Used Meter` appears after the marketplace script is installed and enabled.

== Release and push policy

The repository may be pushed to the maintainer fork after all validation layers are green:

* workflow contract check;
* installer selftest;
* patch apply check against clean upstream source;
* white-box regression tests;
* AlmaLinux minimal install/update/uninstall cycle;
* GUI evidence for every feature in `feature-matrix.json`;
* no temporary test files left in the repository, `$TMPDIR`, project work directories, or container cache.

If GitHub Actions is used for publication, prefer a manually triggered release job with explicit `contents: write` permission and a repository secret such as `FORK_PUSH_TOKEN`.
Scheduled jobs should report status but should not push unreviewed adaptations automatically.

== Repository hygiene

Podman container files, local storage configuration, cache directories, and transient test work directories must stay out of Git.
Upstream source and release artifacts are a maintainer policy decision: do not exclude or delete `CodexPlusPlus/`, `codex-desktop-linux/`, source snapshots, or release archives merely because they came from upstream.
If those artifacts are added later, document why they are needed and which upstream version or tag they represent.
